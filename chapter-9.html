Развёртывание и капстоун: KAN, которой пользуются

Модель в блокноте — это эксперимент. Модель, к которой есть удобный доступ, проверка входа, тесты и ограничения, — это продукт. Соберём сервис, проверим его и составим план собственного проекта.

Глава 9 из 9 ≈ 60 минут сервис · тесты сложность: средняя

Работает у меня — не значит работает у пользователя. Народная инженерная мудрость

Зачем эта глава

Модель, которой не может воспользоваться другой человек, остаётся экспериментом. Здесь обязательный финал: демо или API, проверка входа, тесты, ограничения и документация. Docker — один из способов запуска, не самоцель; «капстоун» — итоговый проект, который вы собираете сами.

От модели к сервису

Обученная KAN — это файл с числами и функция инференса. Чтобы ей могли пользоваться люди, нужны ещё четыре вещи:

СлойЗадачаВ нашем примере
ИнференсПревратить вход в вероятностиpredict() на Python и JS
ИнтерфейсДать человеку ввести данные и увидеть ответdemo.html
APIДать доступ программамcode/serve_pure.py
НадёжностьВалидация, тесты, логи, мониторингcode/test_predict.py, проверки диапазонов

Не начинайте с Kubernetes и микросервисов. Начните с одного статического файла и одного HTTP-эндпоинта. Если модель полезна, инфраструктура вырастет вместе с нагрузкой.

Что значит «пользуются»

Человек открыл страницу, ввёл свои данные, получил понятный ответ и понял ограничения. Программа отправила JSON и получила JSON. Этого достаточно для первого релиза. Красивая обёртка не компенсирует нечестную модель, а честная модель без интерфейса остаётся экспериментом.

Статическое демо: без сервера

Самое дешёвое развёртывание — статическая страница. У нас уже есть demo.html: она загружает веса из assets/iris_model.js и считает всё в браузере. Ни Python, ни сервер, ни интернет не нужны.

Такой вариант хорош, когда:

  • модель маленькая и её веса не секрет;
  • нужен офлайн-доступ или демонстрация на слабом ноутбуке;
  • нет необходимости хранить историю запросов.

Ограничения тоже честные: любой может прочитать веса, нет аутентификации и логирования, а обновление модели требует заменить файл на клиенте. Для публичного сервиса с приватными данными нужен серверный API.

Не кладите секреты в статику

Всё, что загружено в браузер, доступно пользователю. API-ключи, персональные данные и «секретные» веса в статическом демо хранить нельзя. Наши веса специально открыты — это учебная модель.

HTTP-сервис без зависимостей

Для полноценного API достаточно стандартной библиотеки Python. Скрипт code/serve_pure.py отдаёт статические файлы книги и обрабатывает два эндпоинта:

GET /api/modelМетаданные и метрикиJSON без весов
POST /api/predictПредсказание по 4 признакамкласс, вероятности, confidence

serve_pure.py — обработчик запроса 
def do_POST(self):
    if urlparse(self.path).path != "/api/predict":
        self._send_json(404, {"error": "not found"})
        return

    length = int(self.headers.get("Content-Length", "0"))
    if length <= 0 or length > MAX_BODY:
        self._send_json(413, {"error": "слишком большой запрос"})
        return

    try:
        payload = json.loads(self.rfile.read(length))
        result = predict([float(v) for v in payload["features"]])
    except (ValueError, TypeError, KeyError) as exc:
        self._send_json(400, {"error": str(exc)})
        return

    self._send_json(200, result)

Обратите внимание на валидацию: сервис не пытается «предсказать хоть что-нибудь» на входе вне обучающего диапазона, а возвращает понятную ошибку 400. Это важнее, чем кажется: молчаливая экстраполяция — источник опасных ответов.

Почему без FastAPI

FastAPI — отличный инструмент, но для одной модели и четырёх чисел хватает http.server. Меньше зависимостей — проще запустить на слабом ноутбуке и в контейнере. Когда появятся десятки эндпоинтов, схемы и авторизация, переход на FastAPI будет оправдан.

Docker и публикация

Контейнер фиксирует окружение: тот же Python, те же файлы, тот же запуск на любой машине. Для нашего сервиса достаточно образа на python:3.12-slim — никаких тяжёлых зависимостей.

code/Dockerfile 
FROM python:3.12-slim

WORKDIR /app

COPY code ./code
COPY assets ./assets
COPY demo.html index.html ./
COPY chapter-*.html ./

EXPOSE 8000

CMD ["python", "code/serve_pure.py", "--host", "0.0.0.0", "--port", "8000"]
терминал 
$ docker build -f code/Dockerfile -t kan-iris .
$ docker run --rm -p 8000:8000 kan-iris
# http://localhost:8000/demo.html

Для публичного доступа нужен HTTPS, reverse proxy (nginx/Caddy), лимиты запросов и логирование. Не выставляйте --host 0.0.0.0 в открытую сеть без этих слоёв. И помните: контейнер не делает модель безопасной — он лишь упаковывает код.

Не загружайте pickle из интернета

pickle и torch.load могут исполнять произвольный код. Для своих весов используйте формат, которому доверяете, проверяйте контрольные суммы и не принимайте файлы моделей от незнакомых людей. Наш JSON — безопасный учебный пример, хотя и он требует валидации структуры.

Тесты, мониторинг и доверие

Модель может сломаться тихо: файл не загрузился, порядок признаков изменился, вход вышел за диапазон. Поэтому минимум — автотесты на инференс и валидацию. В проекте есть code/test_predict.py:

test_setosa ... ok
test_versicolor ... ok
test_virginica ... ok
test_wrong_length ... ok

Ran 5 tests in 0.001s
OK
Что проверятьПримерПочему
Формат входа4 числа, не 3 и не 5Иначе индекс уйдёт не туда
Диапазон4.3 ≤ sepal_length ≤ 7.9KAN не умеет экстраполировать
ТипNaN/∞ отклоняютсяИспортят вероятности
Сумма вероятностей≈ 1.0Признак корректного softmax

В продакшене добавляют мониторинг: распределение входов, долю отказов, уверенность модели, задержку и обратную связь. Если входы начали смещаться (data drift), точность может упасть без единой ошибки в коде. Тогда модель переобучают на новых данных и снова проверяют.

Что логировать, а что нет

Логируйте версию модели, время, тип ошибки и агрегированные метрики. Не храните персональные данные без необходимости и согласия. Для медицинских, финансовых и юридических решений нужны отдельные требования, аудит и человек в контуре.

Капстоун: свой KAN-сервис

Теперь у вас есть все части. Соберите собственный проект по этому чек-листу. Он специально линейный: не переходите к следующему пункту, пока не выполнен предыдущий.

  1. Задача. Одна узкая задача с числовым или категориальным ответом. Не «сделать ИИ», а «предсказать X по Y».
  2. Данные. Соберите таблицу, проверьте пропуски, дубликаты и диапазоны. Зафиксируйте, откуда они и можно ли их использовать.
  3. Baseline. Самое частое значение, линейная модель или маленький MLP. Без baseline вы не узнаете, полезна ли KAN.
  4. Split и метрики. Train/val/test, стратификация, CV, метрика под задачу. Тест — один раз.
  5. KAN. Начните с одного слоя, G=3–5, k=3. Нормализуйте входы в [−1, 1]. Подберите learning rate и число шагов.
  6. Сравнение. KAN vs baseline при одинаковом бюджете. Запишите accuracy/MSE, время, разброс по seed.
  7. Экспорт. Сохраните веса и нормализацию в JSON. Сделайте модель-карточку (пример: code/MODEL_CARD.md): данные, метрики, ограничения.
  8. Интерфейс. Статическая страница или API. Валидация входа, понятные ошибки, ограничения на экране.
  9. Тесты. Хотя бы 5 тестов: корректный вход, границы, неверная длина, неверный тип, известный пример.
  10. Деплой и мониторинг. Локальный сервер, контейнер или хостинг. Логи, версия модели, алерт на рост ошибок.

Критерий готовности

Проект готов, когда незнакомый человек открывает ссылку, вводит свои данные, получает ответ, видит ограничения — и вы можете объяснить, на каких данных и с какой метрикой обучена модель. Всё остальное — улучшения.

Этика и высокая цена ошибки

Не применяйте учебную KAN для медицинских, юридических, финансовых или кадровых решений. На маленьком наборе она не отражает реальный мир. Если цена ошибки высока, нужны валидация экспертом, человеческий контроль, объяснимость и право на апелляцию.

Упражнения

  1. Зачем сервису отклонять вход вне обучающего диапазона, если KAN всё равно вернёт какое-то число?
  2. Почему не стоит загружать pickle с весами из интернета?
  3. Что логировать в сервисе, а что — нет? Приведите по два примера.
  4. Как заметить, что данные «уплыли» и модель устарела?
  5. Какие поля вы включите в модель-карточку для своей KAN?
  6. Составьте план капстоуна для своей предметной области: задача, данные, baseline, метрика, интерфейс.
  7. Чем статическое демо отличается от HTTP API и когда нужно каждое?
Ответы и комментарии
  1. За пределами [min, max] сплайн экстраполирует, и ответ становится непредсказуемым. Лучше честная ошибка 400, чем уверенно неверный ответ.
  2. pickle может исполнять произвольный код при загрузке. Используйте доверенные форматы, проверяйте источник и контрольные суммы.
  3. Логировать: версию модели, время, тип ошибки, агрегированные метрики. Не логировать без необходимости: имена, точные адреса, медицинские данные, содержимое запросов.
  4. Сравнивать распределения входов с обучающими, следить за долей отказов, уверенностью, точностью на размеченной подвыборке и обратной связью пользователей.
  5. Название и версия, задача, данные и их происхождение, архитектура, число параметров, метрики CV/test, ограничения, дата, автор, лицензия.
  6. Например: предсказание урожайности по погоде и почве; данные — CSV за 5 лет; baseline — среднее по региону; метрика — MAE; интерфейс — форма + API.
  7. Статическое демо работает в браузере без сервера и подходит для открытых моделей и офлайна. API нужен для приватных данных, логирования, авторизации и интеграций.

Итоги части II и всей книги

Мы прошли полный путь: от «что такое обучение» до работающей KAN, которой можно пользоваться. Вторая половина книги добавила то, чего не хватало части I:

  • Данные и оценка. Split, нормализация только на train, метрики, кросс-валидация, baseline.
  • Реальная модель. KAN 4 → 3 на Iris, 111 параметров, 95.3% ± 2.7% в CV, сохранение весов и живое демо.
  • Претрейн и LLM. Честное объяснение двухэтапного обучения, эксперимент с warm start и границы применимости KAN.
  • Развёртывание. Статическая страница, HTTP API без зависимостей, Docker, тесты, мониторинг и капстоун-план.

Что вы теперь умеете

Объяснить, как работает нейросеть и KAN. Собрать данные, обучить модель, честно её оценить, сохранить веса, поднять сервис и показать результат людям. Это и есть минимальный полный цикл ML-инженера — на маленьком, но настоящем примере.

Дальше можно двигаться вглубь: свёрточные и графовые KAN, KAN-трансформеры, PDE и научные вычисления, эффективные реализации базиса, теория приближения. Но теперь у вас есть главное — работающий скелет проекта, который можно заменить своей задачей.

Финальное упражнение

Возьмите свои данные, повторите путь из главы 7 и замените Iris. Если модель окажется полезной — разверните её по главе 9 и дайте ссылку человеку, который не знает, что такое KAN. Если он сможет воспользоваться и понять ограничения, вы достигли цели.

Спасибо, что дошли до конца. Дальше — только ваши данные, ваши вопросы и аккуратные эксперименты.
